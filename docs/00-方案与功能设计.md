# 微信群 AI 助手 · 方案与功能设计（v0.1）

> 目标：在**你自己的微信群**里内置一个 DeepSeek 助手，能聊天、看图、看视频、联网、分享 B 站视频，可自定义人格，有错误日志和日记，记忆能滚动保留 3 个月且更新不丢。
>
> 本文分两部分：**第 0~3 章是可行性判断（重要，先看）**，**第 4~11 章是功能与工程设计**。

---

## 0. 一页结论

| 你的需求 | 能否做到 | 怎么做 |
|---|---|---|
| 群里聊天调用 DeepSeek | ✅ | `deepseek-flash` 官方 API |
| 发图 / 理解图片 | ✅ 官方原生 | `deepseek-flash` 支持图像输入（2026-10 文档确认） |
| 理解视频 | ✅ 需拼装 | ffmpeg 抽关键帧 → 视觉模型 + 音频转文字 |
| 实时联网知识 | ✅ 官方原生 | DeepSeek 官方 Search / Fetch API（5 元 / 1000 次） |
| 分享 B 站视频 | ✅ | B 站公开 API 解析 + 字幕总结 + 链接卡片 |
| **不被封号** | ⚠️ **无法保证** | 只能用「小号 + 严格风控」把概率压到最低，详见第 6 章 |
| 自己给 DeepSeek 设定人格 | ✅ | 三层人格配置 + 版本回滚 |
| 错误日志 | ✅ | 结构化日志 + 指纹聚合 + Web 面板检索 |
| 日记 | ✅ | 每晚自动生成，可查、可导出 |
| 记忆拉长到 3 个月 + 更新不丢 | ✅ | 四层记忆 + append-only 事件日志 + 每日备份 |

**一句话结论**：DeepSeek 侧的技术障碍已经基本不存在（视觉、联网都是官方的），**唯一的真实风险在微信账号侧**——微信没有给个人群开放机器人接口，任何自动收发消息的方案都属于第三方手段。所以本方案的核心取舍是：**功能最强的路线（本地 hook）+ 专用小号 + 严格风控**，而不是去找"绝对不封"的银弹（不存在）。

## 2. 微信侧可行性（最关键的一章）

> ## ⛔ 重要更新（2026-10-23 实测）：A 路线（3.9 hook）地基已塌
>
> 装好微信 3.9.12.17 后扫码登录，服务器直接弹窗 **「当前微信版本过低，请升级至最新版本」**，无法进入。
>
> - 这是**服务器端版本封禁**，不是本地配置问题：改 hosts、改版本号、重装都不管用。
> - 社区已知：wechatferry 仓库 [Discussion #74](https://github.com/wechatferry/wechatferry/discussions/74)（2026-01-17 提出）至今 **0 条回复**，无人给出解法。
> - WeChatFerry SDK 写死 v39.4.5，只认 3.9.12.17，**没有 4.x 版本**。
>
> **结论**：除非有某个能在 3.9 上登录的老账号（未在 4.x 上使用过），否则 A 路线不可用。
> 备选路线见本章 2.2 表格中的 B（wxauto）与 C（企业微信）。
> 本项目已把接入层做成可替换适配器（`src/adapters/`），换路线不改业务代码。
>
> ## ✅ 最终解法（2026-10-23 实测通过）
>
> **wechatauto（PyPI: `wechatauto_replica`，Apache-2.0）** —— 保持最新微信 4.1.15.56，不降级、不注入 hook、不花钱：
> - 收消息：解密本地 SQLCipher 4 数据库（不依赖 UIA）
> - 发消息：UIA + OCR 混合驱动；它会热激活微信里关闭 UIA 的内存标志（`Weixin.dll+0xb39c9d8: 0 -> 1`）
> - 实测：179 个会话可读、7029 条历史可读、往文件传输助手发送成功
>
> 详见 [微信接入：wechatauto](02-微信接入-wechatauto.md)。
> 注意：wxauto（含 ¥200 的 Plus）**不可用**，因为微信 4.1.15 的 UIA 树本身是空的。

### 2.1 先说实话

微信**没有**面向个人群的开放机器人 API。你想的「在微信群里内置一个机器人」，只有三条路：

1. **本地 hook**（往微信客户端注入 DLL，接管消息收发）——功能最全，但违反微信使用协议，理论上有封号风险。
2. **UI 自动化**（模拟人点界面，不注入内存）——技术手段更"温和"，但依赖窗口开着，稳定性差，通常收费。
3. **官方通道**（企业微信 / 微信客服 / 公众号）——完全合规、零封号，但**形态不是"个人微信群"**。

所以"不要被封"这个要求，准确的说法是：**选对路线 + 用小号 + 把行为做得像人，把概率压到很低**。任何人跟你保证"绝对不封"都是骗你的。

### 2.2 三条路线对比

| 维度 | **A. WeChatFerry（本地 hook）** | **B. wxauto v4.0（UI 自动化）** | **C. 企业微信智能机器人 / 微信客服（官方）** |
|---|---|---|---|
| 能用你现在的微信 4.1 | ❌ 需另装 **3.9.12.17** | ✅ 支持 4.x | — |
| 形态 | 个人微信群 ✅ | 个人微信群 ✅ | 企微群内 @机器人 / 1:1 客服 ❌ 个人群 |
| 收消息 | ✅ 实时全量 | ✅ 轮询界面 | ✅ 回调（需企微认证） |
| 发文本/图片/文件 | ✅ 全支持 | ✅ 支持 | ✅ 支持 |
| 发链接卡片（分享 B 站） | ✅ 可发 XML 卡片 | ⚠️ 只能发链接文本 | ✅ 支持 |
| 引用回复 / @ | ✅ | ✅ | ✅ |
| 开发语言 | **Node（现成生态）** | Python（本机没装） | 任意 HTTP |
| 费用 | 免费开源 | **需购买激活码** | 免费（部分能力需企业认证） |
| 封号风险 | 中 | 低 | **零** |
| 稳定性 | 高（后台运行） | 中（微信窗口必须在、不能最小化） | 高 |
| 适合你吗 | **推荐主方案** | 备选 | 如果你完全不想冒险 |

**我的建议：A 为主。** 理由：
- 你本机 Node 齐全，`@wechatferry/core` 是现成 Node 生态（还带 Wechaty 兼容层）；
- 免费、功能最全（XML 卡片、引用、群管理、发文件都能做，B 站分享才做得漂亮）；
- 微信 3.9.12.17 可以和 4.1 **并行安装**（不同目录、不同数据目录），不影响你日常用 4.x；
- 机器人用**小号**跑，主号完全不受影响。

**C 作为保底**：如果你后来觉得风险不能接受，我可以在同一套业务代码上换一个"微信适配层"，改用企业微信智能机器人。所以架构上我会把「消息接入」做成可替换的适配器（见 7.3），换路线不重写业务。

### 2.3 A 路线必须先做的准备（约 40 分钟）

1. 下载并安装 **微信 3.9.12.17**（历史版本仓库 `tom-snow/wechat-windows-versions`），装到独立目录（如 `D:\WeChatBot\`），**关闭自动更新**。
   - 直连 GitHub 慢，用 `https://gh-proxy.com/` 前缀。
2. 准备**机器人小号**（重要，见 6.1），在这台 3.9.12.17 上登录并保持在线。
3. 把这个小号拉进你的群（或建一个测试群）。
4. 装 ffmpeg 静态版（视频/语音要用），解压到 `tools\ffmpeg\` 即可，不写注册表。

> ⚠️ 注意：微信客户端**同一账号不能同时在 3.9 和 4.x 上登录**。所以小号只登 3.9，你的主号继续用 4.x，两不干扰。

## 3. DeepSeek 能力盘点（2026-10 官方文档确认）

这块是好消息：你要的多模态和联网，官方都给了。

| 能力 | 模型 / 接口 | 说明 |
|---|---|---|
| 文本对话 | `deepseek-flash` | 1M 上下文、最大 384K 输出、支持思考模式开关 |
| 强推理 | `deepseek-v4-pro` | 更强但**不支持图片**，价格约 4.5~9 元/百万输入 |
| **图像理解** | `deepseek-flash` | JPEG/PNG/GIF/WebP；base64 / URL / Files API 三种传法；**每张图最多 1024 tokens** |
| 工具调用 | 两者都支持 | 可以让模型自己决定要不要检索、要不要查 B 站 |
| JSON 输出 | 两者都支持 | 用于结构化抽取记忆、生成日报 |
| **联网搜索** | `POST /v1/tools/search` | 返回 title/url/snippet/summary/content，`after:` / `site:` 等语法 |
| **网页抓取** | `POST /v1/tools/fetch` | 返回 Markdown 正文 |
| 价格 | 闲时 1 元 / 百万输入、4 元 / 百万输出；高峰 2 / 9 元 | 周一至周五 9-12、14-18 为高峰，其余半价 |
| 联网计费 | Search / Fetch 各 5 元 / 1000 次成功请求 | 有结果才计费 |

**对我们的设计有 3 个直接影响：**
1. **不需要再买第三方视觉模型**（通义/智谱/豆包都不用了），图片直接喂 `deepseek-flash`。
2. **联网用官方 Search API**，不用爬 Bing/Google，不会因为反爬而挂。
3. **聊天默认关思考模式**（快、便宜），遇到数学/代码/推理题自动切到思考模式——这个要写进路由器。

**唯一缺口：视频没有原生支持。** 方案：
```
视频消息(mp4) → ffmpeg 均匀抽 6~8 帧 → deepseek-flash 逐帧/拼图理解
              → ffmpeg 抽音轨 → ASR 转文字（见下）→ 合并成"视频摘要"
```
音频转文字需要一个第三方（DeepSeek 没有 ASR）：优先用**硅基流动 SenseVoice**（便宜/有免费额度），或本机跑 `faster-whisper`（要 Python，且占内存）。这一项做成**可开关的可选能力**，不影响主流程。

## 5. 记忆系统设计（重点：3 个月滚动 + 更新不丢失）

这是整个项目技术上最有价值的部分，也是你最该关注的部分。

### 5.1 四层记忆（越往下越"压缩"，越往上越"原始"）

```
L0 原文层    最近 90 天的原始消息/对话（按 token 预算动态裁剪）
   ↓ 每 30 轮 或 每 2 小时，压缩一次
L1 摘要层    把一段对话压成结构化要点（带时间、参与人、结论）
   ↓ 每晚 23:30
L2 日记层    当天群聊的自然语言日记 + 结构字段（话题/金句/待办/情绪）
   ↓ 每周 / 每月
L3 画像层    群体画像、成员画像、长期事实、约定与偏好（pinned 永不过期）
```

**"拉长到 3 个月"的含义**：
- 检索时**不是**只看最近几十条，而是跨 90 天做混合检索（L1/L2/L3 + 归档的 L0 索引）；
- 90 天是**默认窗口**（可配 30~365 天），窗口内的原文可以直接引用；
- 超过 90 天的原文**不删除**，归档成 `archive/2026-07.jsonl.gz`，全文索引保留 → 你说"三个月前那个事"，它还能查出来。

### 5.3 记忆怎么"更新而不丢"

这是很多机器人做砸的地方（一压缩，前面的就没了）。三道保险：

**保险 1 · append-only 事件日志**
所有输入输出先写 `events`（只追加），再更新派生表。**任何一张表被写坏，都能从 events 重建。** 定时任务每天核对 `events` 与 `messages` 条数，对不上就告警。

**保险 2 · 蒸馏可追溯**
每次压缩 L0→L1、L1→L2、L2→L3，都记录 `source_ids`（源消息 id 列表）。所以：
- 摘要里说的每句话，都能点开看原文；
- 误压缩可以**回滚**：删除某条 L1，从 L0 重新生成；
- 记忆支持"纠错"：`/忘掉 3` 或面板里改，旧版本进 `revisions` 留痕。

**保险 3 · 备份 + 归档不删除**
- 每日 03:00 自动备份（SQLite 在线备份 API，不锁表）→ `backups/db-2026-10-23.sqlite`，保留 30 份；
- 每周导出一次全量 JSONL（人类可读，防"数据库坏了就全没了"）；
- **升级/迁移前强制快照**；
- 90 天归档只压缩不删，索引保留；
- 数据库 `PRAGMA user_version` 做 schema 版本号，迁移脚本先备份再跑，失败自动回滚。

### 5.4 检索流程（每次回答前）

```
用户问："上次说的那个考研时间安排来着？"
  ① 无条件注入：pinned memories（≤800 tokens）
  ② 混合检索：trigram FTS + (可选)向量，跨 L1/L2/L3，取 top 8
     排序分 = 相关度 × exp(-Δ天数 / 30)      ← 时间衰减，新的更靠前
  ③ 最近 3 天的 L1 摘要（≤1500 tokens）
  ④ 最近 20 轮 L0 原文（≤4000 tokens）
  ⑤ 按预算裁剪 → 拼进 system/user
```
总预算约 9~12k tokens，远低于 1M，**便宜且准**。核心原则：**不是把所有东西塞进去，而是把"该记的"检索进来。**

### 5.5 记忆蒸馏的触发策略

| 层级 | 触发 | 输出 |
|---|---|---|
| L0→L1 | 每 30 轮 / 每 2 小时 / 话题切换 | 3~8 条要点＋结论＋待办 |
| L1→L2 | 每晚 23:30 | 日记（第一人称，拟人） |
| L2→L3 | 每周日 / 每月 1 号 | 长期事实、成员偏好、群体约定 |
| 显式 | `/记住` 指令 | 直接进 L3，pinned |

LLM 抽取时用 **JSON 输出**（DeepSeek 支持），字段固定，避免"摘要越来越水"。抽取 prompt 里强制要求：只记**稳定事实**，不记闲聊；每条带置信度，低于阈值丢弃；与已有记忆去重（相似度 > 0.9 的合并）。

## 6. 防封设计（五层）

> 前提：**没有 100% 不封的方案**。下面是把风险从"高"压到"很低"的具体做法。

### 6.1 账号层（最重要，收益最大）
1. **用专门小号**，绝不用主号。独立手机号，注册满 1 个月，有正常聊天/朋友圈记录（"养号"）。
2. 小号**只在自己的群/白名单群**里活动，不进陌生的营销群、不群发。
3. **不登网页版微信**、不同一账号多端同时挂机器人。
4. 准备 **2 个小号**轮流用：一个被限制时立刻换另一个，业务不中断（记忆库是共用的，换号不丢）。

### 6.2 行为层（让它像人）
| 项 | 默认值 |
|---|---|
| 触发方式 | 只回 @ 和 `/` 指令（群里默认**不**全量回复） |
| 随机延迟 | 1.2~4.5 秒（模拟看消息+打字） |
| 分段发送 | 长回答拆 2~3 段，段间 0.8~2 秒 |
| 单群频率 | ≤ 20 条/小时，≤ 120 条/天 |
| 全局限速 | ≤ 3 条/分钟 |
| 夜间静默 | 23:30~07:00 不回（可配） |
| 主动行为 | ❌ 不加好友 ❌ 不发红包/转账 ❌ 不群发 ❌ 不主动 @所有人 ❌ 不发名片/二维码 |

### 6.3 内容层（防举报）
- 敏感话题过滤：政治、色情、赌博、医疗诊断、荐股、代写论文/作业、涉未成年人。
- 输出里不出现"加我微信""扫码领""内部渠道"这类**营销话术**（最容易被举报）。
- 单条回复 ≤ 600 字，超长改成"合并转发"或提示私聊。
- **群公告告知**："本群有 AI 助手，会记录消息用于回答"——合规，也降低群友反感导致举报的概率。
- 群里有人明确说"别记我"→ `@机器人 别记我` 立即对该用户关闭记忆。

### 6.4 监控层（出事立刻停）
- 掉线 / 被踢 / 需要验证 / 发送连续失败 → **立刻停止所有发送**，不再重试（异常行为连发是最危险的）。
- 告警：面板红条 + 邮件/Server酱推送到你手机。
- 看门狗：进程挂了自动重启；但**风控熔断后不自动重启**，等你人工确认。

### 6.5 合规层
- 只存必要数据，全部本地，不对外提供服务，不卖数据。
- 提供一键清除（`/清除我的数据`），日记和记忆可导出、可删除。
- 不用于营销、群控、批量加人——**那才是真正高封号的用法**。

### 7.4 关键工程细节（容易踩坑的地方，我会提前处理）

1. **微信会掉线**：断线要自动重连，重连后要**去重**（同一条消息可能重复推送），并且**补课**（断线期间的消息）。
2. **发送失败要缓存重试**，但**风控类失败不重试**（区分 error code），否则越重试越危险。
3. **图片/视频要落盘缓存并设过期清理**（微信图片 URL 会过期，必须当场下载）。
4. **中文检索**：trigram 需 ≥3 字，2 字查询走 LIKE 兜底。
5. **模型输出要清洗**：去掉 markdown 里的 `###`、`**` 在微信里不渲染，转成微信友好的纯文本/emoji 列表。
6. **分段发送要断在句号/换行**，不能把代码块切碎。
7. **并发**：同一群同时来 5 条消息，要排队串行处理，避免上下文错乱 + 触发限流。
8. **配置热更新**：改人格/开关不用重启（落 DB + 内存缓存 + 失效通知）。
9. **npm 必须带 `--cache` 指向工作区**，否则 EPERM（已实测）。
10. **`node:sqlite` 是较新 API**，要封装一层，方便以后换 better-sqlite3。
